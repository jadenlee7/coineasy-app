# Case Files 2.0 — playable prototype

## Product decision

Build 113 founder feedback: Receipt Detective / Case File 01 felt closest to a
real app. The next prototype connects a conversation, a simulated wallet, and
a transaction receipt into one short task. Success means changing the right
setting or completing a reviewed mock transfer, not selecting a detached quiz
answer. This is a hypothesis about fun and transfer of learning, not a measured
retention improvement.

Entry: authenticated Daily Run → Practice Arcade → Case Files 2.0.
The original three Practice missions remain available for comparison.

## Three cases

| Case | Interaction | What completion means |
| --- | --- | --- |
| Missing USDC | Read the friend's message, inspect the successful Base receipt and recipient, change the wallet's displayed network from Ethereum to Base | An existing Base balance becomes visible. No new transfer is generated by changing networks. |
| Same ends, different address | Expand both full addresses and compare the middle as well as the prefix and suffix | Stop and tell the friend the receipt belongs to another recipient. The transaction is not reversed or repaired. |
| First delivery | Read the request, fill the fictional address, choose network/token, enter an amount, review, simulate the transfer, inspect its receipt | One local transfer record and the corresponding virtual balances. ETH gas and USDC amount are separate. |

Each case has three deterministic fixture variants with different contact,
amount, and address data. Replay rotates variants. These are authored scenarios,
not a claim of infinitely generated cases or live blockchain records.

## Interaction rules

- Keep `연습 모드 · 가상 자산` visible on every screen, including review and result.
- Tappable controls actually navigate, expand data, change a setting, or advance
  the scenario. No decorative input, dead icon, or external link is required.
- Display the whole address when comparing; matching abbreviated ends is not
  proof that two addresses match.
- Let users make mistakes, read a concise explanation, and correct the same
  step. Do not end the run or reward rushing a financial decision.
- Require receipt evidence before declaring investigation cases solved.
- Changing a transfer field or leaving the app invalidates the old review.
  Confirmation acts on the freshly reviewed draft only and cannot transfer twice.
- Use a short case-closed response, local completion stamps, and a replay button.
  Stamps are session-only; they are not Orange points, transferable rewards, or
  a persisted achievement system.

## Implementation boundary

All case data and virtual balances live in the screen's memory. Fixture address
fill is internal to this game, not a system clipboard read. Typed amounts and
addresses are never sent or persisted. There is no wallet SDK, RPC, signing,
transaction broadcast, Squid execution, backend request, storage, or migration.
No actual network transaction is represented by a fixture hash.

The candidate retains buildNumber 113 and the existing disabled W0 gate. A future
TestFlight binary requires a separate release step; installing Build 113 does
not install this prototype. No EAS or Railway deployment is part of this change.

## Device QA and playtest

### Local verification — 2026-09-05

| Area | Test level / target | Observed result |
| --- | --- | --- |
| Case rules and financial-learning boundaries | Pure state-machine tests: all 3 cases, all 3 fixture variants, malformed inputs, stale review, duplicate confirm, read-only completed cases | 9 Case Files tests passed; full mobile suite 322/322 passed |
| Playable flow and feedback | Actual `CaseFiles.js` rendered with React Native Web; complete each case, reject a wrong diagnosis/amount, replay, close, leave review, simulate document visibility changes | Passed; no page errors or external requests during the isolated session |
| Narrow layout | 320, 390, 430 CSS-pixel widths; inspect controls and screenshots | No horizontal control overflow observed; notices and completion headings visible after actions |
| Native bundle integration | `EXPO_NO_DOTENV=1 npx expo export --platform ios` | Passed: 2,695 modules / 125 assets; bundle `entrypoint-4914ba64b77783ec6217c6de32445980.js` |
| Physical device | iPhone keyboard, safe area, VoiceOver, large text, OS lifecycle and authenticated navigation | Not observed; requires a separately approved TestFlight candidate |

The browser harness uses the actual screen and engine, with native haptics,
safe-area handling, navigation, and icons replaced by local preview adapters.
Browser visibility simulation is not physical iOS background QA. Preview-only
dependencies were installed outside the repository; app dependency files are
unchanged. Screenshot and interaction evidence is kept outside the source tree
in the task's `artifacts/case-files-v2` folder.

An independent UI review found that bottom-of-form actions could place error
feedback above the viewport. The screen now brings notices and review context
into view, and scrolls to the case-closed result. Interaction tests checked the
visible feedback rather than just the state transition.

At the 2026-09-05 local verification checkpoint, no commit or remote PR had been
created. The 2026-09-06 continuation covers commit, push, and a Draft PR only;
the mobile suite was re-run and passed 322/322. Merge, W0 activation,
build-number changes, EAS build/submission, and backend operations remain outside
this candidate's scope.

Candidate device checks (not yet observed):

- Open from an authenticated Daily Run; close and reopen each case.
- Case 1: inspect the receipt, switch networks, verify that only the displayed
  balance changes and no outgoing transaction is added.
- Case 2: compare full addresses; verify that equal ends do not pass and that
  completion does not claim to recover the funds.
- Case 3: try wrong network, wrong token, malformed address, empty/negative/too
  large amount. Correct the fields, review, edit, and review again.
- Double-tap the simulated confirmation; verify one debit and one receipt.
- Background during review, return, and verify a new review is required.
- Small screen, large text, keyboard open, and VoiceOver: reach all controls,
  read full addresses, and hear feedback without clipping or blocked scrolling.
- Replay all three variants and move between cases without stale data.

Founder / 10-person beginner pilot: let each person start the first case without
a walkthrough. Observe completion time, where help is needed, whether they can
explain the outcome, and whether they start another case without prompting.
An initial directional target is 6/10 voluntarily starting a second case and
8/10 correctly interpreting a new receipt after play. These small-sample targets
are not proof of retention. Ask for a 1–5 fun score and one concrete reason.
Do not add telemetry to run this pilot; a consented observer can record these
anonymous aggregate results.

## Follow-up options

After this prototype is played, consider a branching DM case or a permission
inspection case. Expansion to live public records, a testnet, or real transactions
is a different scope. First validate that the current three cases are both
understandable and worth replaying.
